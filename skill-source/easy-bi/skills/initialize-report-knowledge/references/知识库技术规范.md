# 知识库 Skill 技术规范

## 1. 适用范围

本规范是 `initialize-report-knowledge` 的唯一详细参考，覆盖工作区、MySQL 连接、多数据库标识、冷热分层、语义默认值、枚举和知识库格式。执行顺序以同目录 `SKILL.md` 为准。

## 2. 工作区与所有权

一个工作区代表一个客户业务系统，可包含多个 MySQL Profile 和数据库。

稳定入口：

```text
workspace.json
config/easy-bi.json
knowledge/index.json
knowledge/scans/
knowledge/drafts/
knowledge/versions/
work/
```

所有路径相对工作区根目录。扫描只新增；草稿可编辑；发布版本不可变；`work/` 可清理。

## 3. MySQL Profile

同一 host、port、凭据和网络边界使用一个 Profile；任一条件不同时使用独立 Profile。

最小配置：

```json
{
  "id": "transport-main-mysql",
  "type": "mysql",
  "host": "127.0.0.1",
  "port": 3306,
  "username": "report_reader",
  "password_env": "EASYBI_MYSQL_PASSWORD",
  "databases": ["database_a", "database_b"]
}
```

第一阶段只支持 MySQL。新增数据库、云存储或其他连接器时使用 Profile 扩展，不改变知识库逻辑标识。

凭据只存在于构建配置或环境变量，不进入扫描、草稿、发布版本和 Bundle。

## 4. 多数据库标识

规范标识：

```text
表：<profile-id>/<database>/<table>
字段：<profile-id>/<database>/<table>/<field>
```

知识库物理导航：

```text
databases/<profile-id>/<database>/
```

跨数据库关系必须同时保存源、目标 Profile 和数据库。没有明确证据时不自动建立跨数据库 JOIN。

## 5. 扫描契约

扫描快照至少记录：

- MySQL 版本；
- Profile 和数据库；
- 表名、注释、引擎和估算行数；
- 字段、类型、可空、默认值和注释；
- 主键、索引和外键；
- Schema fingerprint；
- 有界的近期活跃度证据；
- 扫描时间和错误。

数据库访问必须只读。活跃度探测：

1. 优先选择有索引的创建或更新时间字段并读取最新值；
2. 无时间索引且配置允许时，对有限候选列查询最近 N 天是否存在数据；
3. 使用短超时或 `MAX_EXECUTION_TIME`；
4. 超时、权限不足或异常记为 `activity_unknown`；
5. 完成查询且无近期记录才是可靠不活跃证据。

扫描失败不能写成“无数据”。

## 6. 分层决策

默认阈值：

```json
{
  "hot_threshold": 80,
  "cold_threshold": 25,
  "inactivity_days": 90
}
```

决策优先级：

1. 人工 `forced_hot`；
2. 已发布报表明确依赖；
3. 当前预期报表的强字段证据；
4. 可靠的 90 天不活跃证据；
5. 技术表、归档表和废弃命名规则；
6. 业务名称、注释、关系和使用信号评分；
7. 阈值。

可靠不活跃默认判冷，但强制热表和强报表依赖覆盖。无可靠活跃度时不能仅因“未发现最近数据”判冷。

强报表证据包括：

- 完整 `table.field` 或 `database.table.field` 命中；
- 同一报表至少两个字段命中同一表；
- 报表名称命中业务实体且至少一个字段命中。

单个未限定的通用字段名是弱证据。

分层内容：

| 层级 | 保存内容 |
|---|---|
| 热 | 完整字段、语义、筛选、关系、枚举和活动证据 |
| 温 | 表及字段摘要、可提升信息、枚举候选 |
| 冷 | 表名、注释、分类理由和活动摘要，不保存字段详情 |

每个结果必须保存 score、evidence 和 final reason，便于人工解释与调整。

## 7. 分层计划与批准

`propose` 只生成计划，不直接构建草稿。计划应包含：

- `plan_format_version`；
- 每张表的 proposed tier、final tier、score 和 evidence；
- 冲突和待确认项；
- 审批状态、审批人和决策摘要。

只有通过 `approve-plan` 或等价的明确人工确认后才能 `build`。手工编辑计划仍受支持，但 CLI 必须校验批准状态。

温表和冷表可以通过 `promote` 提升。冷表提升时必须从原扫描恢复字段详情，不能根据冷表摘要猜测。

## 8. Catalog 结构

知识库格式版本为 `catalog_format_version=3`。

```text
<catalog>/
├── manifest.json
├── databases/
│   └── <profile>/<database>/
│       ├── database.json
│       ├── hot/<table>.json
│       ├── warm/<table>.json
│       └── cold/<table>.json
├── global/
│   ├── enums.json
│   └── relationships.json
├── reviews/
│   ├── inference-summary.json
│   └── blocking-issues.json
└── indexes/
```

`databases`、`global` 和 `reviews` 是知识源；`indexes` 是可重建派生文件。

Manifest 至少保存：

- 格式和业务版本；
- draft/published 状态；
- 源扫描 ID 与 hash；
- Profile 和数据库清单；
- 分层数量；
- 创建、发布和审批信息。

发布时复制到 `knowledge/versions/<version>` 并更新 `knowledge/index.json`。禁止覆盖已有版本。

## 9. 表语义

表文档应区分：

- 物理元数据；
- `semantic.name`、`semantic.label` 和业务说明；
- 字段角色、展示和筛选策略；
- 逻辑删除、租户、组织和用户上下文；
- 已确认关系与候选关系；
- 枚举引用；
- inferred/confirmed 状态；
- 人工覆盖记录。

重新扫描可以更新物理变化，但不得覆盖人工确认的 label、说明、筛选、关系和枚举标签。

## 10. 默认语义

优先级：

1. 用户明确配置；
2. 已发布知识与人工确认；
3. 报表需求中的 label/filter；
4. 数据库注释和原生定义；
5. 命名约定；
6. 保守默认值。

常见角色：

| 模式 | 默认角色 | 默认筛选 |
|---|---|---|
| `id`、`*_id` | 标识或关系键 | 精确，通常不展示 |
| `code`、`*_code`、`*_no` | 业务标识 | 精确，可选 `in` |
| `name`、`*_name`、描述 | 文本 | 模糊匹配 |
| 创建/更新时间 | 时间 | 范围 |
| 日期 | 日期 | 范围 |
| 数量、金额、重量 | 数字 | 等于和范围 |
| 原生 ENUM/SET 或明确码值 | 枚举 | 单选/多选 |
| `tenant_id` | 租户上下文 | 隐藏，可选传入 |
| `is_delete` 等 | 系统条件 | 隐藏固定值 |

纯中文字段名可以通过唯一 `semantic.name` 或 `semantic.label` 解析；多义时返回 `FIELD_AMBIGUOUS` 和候选 `table.field`。

只有阻断项才能提问。每阶段最多一个合并问题，不生成逐表固定问卷。

## 11. 关系

关系来源：

- 数据库外键；
- 唯一、保守的 `_id → id` 同库候选；
- 用户确认；
- 已发布知识。

候选关系必须标记 `inferred/unverified`，不能被报表生成器当作已确认 JOIN。跨数据库和非唯一候选进入阻断清单。

## 12. 枚举

`global/enums.json` 包含：

```json
{
  "bindings": [
    {
      "table_id": "profile/database/table",
      "field": "status",
      "dictionary_name": "order_status"
    }
  ],
  "dictionaries": [
    {
      "name": "order_status",
      "values": [
        {"value": "NEW", "label": "新建"}
      ]
    }
  ]
}
```

初始化来源：

1. MySQL 原生 ENUM/SET；
2. 字段注释中的明确 code/中文定义；
3. 有界、超时、只读的 `SELECT DISTINCT`；
4. 已有人工配置。

初始化和重扫可以补充新 code，但不得覆盖已有中文 label。

通用字段 `status`、`type`、`source`、`flag`、`category`、`level`、`mode` 默认不跨表合并。只有字段名、规范化注释和完整类型一致，并有相同原生值或明确值证据时才自动共享；用户也可以指定同一字典名。

Excel 固定两个 Sheet：

- `枚举字段绑定`：连接、数据库、表、字段、字段说明、枚举名称；
- `枚举值映射`：枚举名称、枚举code、中文名称、说明。

不存在枚举 ID、排序、启用和确认字段。Code 按文本保存。导入前先 dry-run；草稿导入是权威配置，发布版本不可导入。

## 13. 审核与发布门禁

自动推断输出到：

```text
reviews/inference-summary.json
reviews/blocking-issues.json
```

阻断项包括：

- 预期报表字段无法解析；
- 同名语义多义；
- forced-hot 冲突；
- 草稿结构无效；
- 枚举发布必需映射不完整；
- 需要用户确认的关系。

非阻断的 ext/JSON 字段、普通说明和未使用枚举不应产生逐项问题。

发布前（仅数据质量与结构完整性，**不再要求语义审核为 approved**）：

- 草稿结构通过（表 ID 唯一、tier 计数与 manifest 一致、冷表不含字段明细、无密钥类字段、`catalog_status` 为 ready/published）；
- 每张热表有可用业务名且状态为 inferred/confirmed、安全范围可用，报表依赖的热表至少暴露一个字段；
- 目标版本不存在。

语义审核的批准环节已移除：人工检查生成的知识库后选择发布，即视为完成审查。语义审核摘要（`reviews/semantic-review.json`、`reviews/blocking-issues.json`）仍会生成，供人工检查参考，但不再阻断发布。语义仍不可用的表应先修正或降级为 warm/cold，而不是阻断整体发布。

## 14. 跨工作区维护

Skill 不写死客户目录。所有位置从工作区根目录和 Bundle Manifest 解析。切换工作区时只读取该工作区自己的配置、Bundle Lock、知识库和报表；任何升级都不得改变其他工作区。
