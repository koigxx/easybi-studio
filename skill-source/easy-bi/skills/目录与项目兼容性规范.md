# Easy BI 开发维护与目录兼容规范

本文件是 Easy BI、两个 Skill、共享 Runtime、Studio 和客户工作区之间的开发维护与目录兼容契约。修改任一 Skill、共享 Runtime、工作区初始化器或 Studio 集成逻辑前，必须先完整阅读本文件。

## 1. 核心原则

Easy BI 项目不依赖 Skill 的内部实现，只依赖稳定的文件目录、格式版本、命令入口和 Runtime 接口。

- Skill 后续升级应优先改进提示词、判断规则、脚本内部实现和依赖，不改变项目已使用的目录。
- 可以在现有目录中增加可选文件或可选字段，但不能随意删除、改名或移动原有入口。
- 新工作区可以使用最新 Skill；已有工作区不得被静默升级。
- 确实需要调整稳定目录时，必须同时提供兼容适配、迁移、校验和回滚，不能要求项目代码到处跟着修改。
- Studio 应通过统一的工作区适配层访问文件，页面组件不能散落硬编码路径。

“项目和 Skill 相对独立”指两者只通过本文件声明的公共契约协作，不代表完全没有依赖。

## 2. 三层目录关系

### 2.1 正式 Skill 源目录

```text
easy-bi/
├── workspace.json
├── config/
├── knowledge/
├── reports/
├── outputs/
├── scripts/
├── skills/
│   ├── index.json
│   ├── bundle.manifest.json
│   ├── 目录与项目兼容性规范.md
│   ├── initialize-report-knowledge/
│   └── create-report-package/
├── toolkit/
│   ├── config/
│   └── contracts/
└── work/
```

正式目录是 Skill 快照的唯一来源。`docs/`、测试源码、TypeScript 源码和 `node_modules/` 不属于部署运行目录。

### 2.2 Studio 内置 Skill 快照

```text
vendor/easybi-bundle/
├── bundle.manifest.json
├── skills/
│   ├── index.json
│   ├── 目录与项目兼容性规范.md
│   ├── initialize-report-knowledge/
│   └── create-report-package/
├── toolkit/
└── templates/
```

Studio 只从正式目录生成版本化快照，不直接修改正式 Skill。快照必须包含本规范。

### 2.3 客户项目工作区

一个工作区代表一个客户业务系统，可以配置多个 MySQL 数据库。

```text
<workspace>/
├── workspace.json
├── config/
│   └── easy-bi.json
├── skills/
│   ├── index.json
│   ├── bundle.manifest.json
│   ├── bundle.lock.json
│   ├── 目录与项目兼容性规范.md
│   ├── initialize-report-knowledge/
│   └── create-report-package/
├── toolkit/
│   ├── config/
│   │   └── runtime.json
│   └── contracts/
├── knowledge/
│   ├── index.json
│   ├── scans/<scan-id>/
│   ├── drafts/<draft-id>/
│   └── versions/<version>/
├── reports/
│   ├── index.json
│   ├── plans/
│   ├── models/<report-id>/
│   └── packages/<report-id>/<version>/
├── outputs/
│   ├── index.json
│   └── files/
├── scripts/
│   └── adapters/
└── work/
```

最小 CLI 工作区可以暂不复制 `skills/`、`toolkit/` 和 `scripts/`；Studio 创建或导出的完整工作区应包含它们。所有跨文件引用必须相对工作区根目录保存，不得写死客户电脑或服务器的绝对路径。

## 3. 项目可以稳定依赖的入口

以下目录和文件属于项目与 Skill 的公共边界：

| 入口 | 用途 |
|---|---|
| `workspace.json` | 工作区身份、格式版本和路径入口 |
| `config/easy-bi.json` | 项目、数据库和预期报表配置 |
| `skills/index.json` | 工作区 Skill 清单 |
| `skills/bundle.manifest.json` | 当前安装 Skill 的能力、入口、目录映射和兼容范围 |
| `skills/bundle.lock.json` | 当前工作区实际安装的 Bundle 版本和文件哈希 |
| `toolkit/config/runtime.json` | Runtime、OSS 和业务接口配置 |
| `knowledge/index.json` | 当前已发布知识库入口 |
| `knowledge/scans/` | 不可变数据库扫描 |
| `knowledge/drafts/` | 人工和 Agent 可编辑的知识库草稿 |
| `knowledge/versions/` | 不可变知识库发布版本 |
| `reports/index.json` | 可用报表及当前版本入口 |
| `reports/plans/` | 报表生成计划 |
| `reports/models/<report-id>/` | 每个报表唯一当前建模包（字段、关系、最小 source lock 与校验和） |
| `reports/packages/` | 具体报表包 |
| `outputs/` | 导出文件和发布制品 |
| `work/` | 可清理临时文件 |

项目还可以依赖以下稳定 CLI：

```text
easybi-knowledge
easybi-report-package
easybi-runtime
```

以及以下 Runtime API：

```text
GET  /api/v1/reports
GET  /api/v1/reports/{reportId}/parameters
POST /api/v1/exports
```

当前格式基线：

| 契约 | 版本 |
|---|---:|
| `workspace_format_version` | `1` |
| `config/easy-bi.json.config_version` | `4` |
| `catalog_format_version` | `3` |
| `plan_format_version` | `2`（只支持 `2`） |
| `report_package_format_version` | `2`（只支持 `2`） |
| `toolkit/config/runtime.json.config_version` | `1` |
| Runtime API | `v1` |

Skill 版本可以独立变化，但每个 Skill 快照必须声明自己支持的上述格式版本。

## 4. 不同目录的修改权限

- `config/easy-bi.json` 和 `toolkit/config/runtime.json`：允许用户、Studio 和 Agent 按 Schema 编辑。
- `knowledge/scans/`：只新增扫描，不修改历史扫描。
- `knowledge/drafts/`：允许人工和 Agent 调整；重新扫描与 Skill 升级不得覆盖人工语义。
- `knowledge/versions/`：发布后不可原地修改。
- `reports/plans/`：允许审阅和重新生成。
- `reports/models/<report-id>/`：允许 Studio 按修订号调整字段白名单和关联关系；保存后必须重新校验、批准和封存。一个报表只保留一个当前模型。
- `reports/packages/<report-id>/<version>/`：版本发布后不可原地修改。
- `outputs/` 和 `work/`：不是知识源，不能被其他模块当作长期契约。
- `knowledge/**/indexes/`：属于派生索引，可重建，不能作为人工语义的唯一来源。

## 5. 允许直接进行的 Skill 更新

只要自动化测试和旧工作区兼容检查通过，可以直接：

- 优化热、温、冷表判断；
- 优化字段语义、筛选条件和枚举推断；
- 优化提示词和交互步骤；
- 调整 TypeScript 私有模块、函数和测试结构；
- 优化 SQL、Excel、OSS 和任务回调的内部实现；
- 在现有对象中增加具有默认值的可选字段；
- 在现有目录中增加可选辅助文件；
- 增加新的 CLI 命令或可选参数；
- 增加新的连接器或存储适配器，同时保留已有实现。

读取方应忽略不认识的可选字段，写入方不得删除仍受支持的旧字段。

## 6. 不能直接进行的变更

以下变更会影响项目，禁止仅修改 Skill 后直接发布：

- 删除、改名或移动第 3 节列出的目录和入口文件；
- 改变已有字段的含义或删除已有字段；
- 改名 Skill ID、CLI 命令或已有命令参数；
- 修改 Runtime `v1` 路径或既有响应语义；
- 改变已发布知识库或报表包的不可变规则；
- 让 Studio 页面直接读取 Skill 私有源码或临时文件；
- 把公共 Runtime 逻辑复制到每一个具体报表包；
- 把真实密码、OSS Key、Token、业务数据或导出文件放进 Skill 快照。

若业务确实要求这些变更，必须提升对应格式或 API 主版本，并执行第 8 节的迁移流程。

## 7. Studio 适配规则

Studio 应提供统一的 `Workspace/Skill Adapter`，集中完成：

- 读取 `workspace.json`；
- 按路径入口定位配置、知识库、报表和输出；
- 读取 Skill 版本和兼容范围；
- 调用稳定 CLI；
- 将不同兼容版本转换成 Studio 内部统一模型；
- 在格式不兼容时阻止执行并展示升级或迁移说明。

页面、路由和普通业务服务不得自行拼接知识库或报表包的深层路径。以后即使目录确实需要调整，也应优先修改适配层和迁移器，不重写 Studio 页面。

## 8. 已有工作区升级流程

1. 检测新 Skill 版本，不自动复制。
2. 对比新 Skill 支持的格式与工作区现有格式。
3. 展示升级内容和目录差异。
4. 对普通升级按 Bundle 策略创建检查点。
5. 获得用户明确确认。
6. 在临时目录完成复制或迁移，再原子替换。
7. 运行依赖检查、`doctor`、结构校验和最小冒烟测试。
8. 成功后记录升级前后 Skill 版本。
9. 普通升级失败时恢复检查点。

不兼容升级还必须：

- 提供明确的升级或停止支持方案；
- 需要保留旧资产时提供可重复执行的迁移、迁移前检查和迁移后校验；
- 不保留旧资产时返回明确版本错误，并由用户确认删除和重新生成；
- 普通数据迁移提供回滚；明确废弃且用户选择删除的资产可以声明不备份、不回滚；
- 更新本规范、相关 Schema、初始化器、Studio 适配层和测试；
- 获得用户对目录或公共接口变化的明确确认。

## 9. Skill 更新前强制检查

每次修改知识库 Skill、报表 Skill 或共享 Runtime 时：

1. 完整阅读本规范。
2. 列出本次涉及的公共目录、格式、CLI 和 API。
3. 判断是内部实现、兼容扩展还是不兼容变更。
4. 全局查找受影响路径，不能只改其中一个 Skill。
5. 保持正式目录、Studio 快照、新工作区模板和现有工作区的公共结构一致。
6. 更新 Skill 版本、`bundle.manifest.json` 及其兼容范围。
7. 验证至少一个旧工作区仍可读取和运行。
8. 运行两个 Skill 的结构校验、单元测试和必要冒烟测试。
9. 确认没有覆盖人工语义、已发布版本和用户配置。
10. 确认已有工作区不会被静默升级。
11. 在交付说明中写明目录是否变化及兼容性结论。

## 10. 开发阶段的变更维护

当前项目处于开发阶段，不维护按日期累积的变更记录，也不要求为每次公共目录调整新增文档。

变更结论直接写入当前有效的稳定入口：

- 产品边界或流程变化更新 `docs/总体架构.md`；
- 开发、测试和发布方式变化更新 `docs/开发维护指南.md`；
- Agent 执行规则变化更新对应 `SKILL.md`；
- 使用步骤变化更新对应 `使用说明.md`；
- 格式、算法或运行约束变化更新对应技术规范；
- 公共目录与升级策略变化更新本文件；
- CLI、逻辑路径和兼容范围变化更新 `bundle.manifest.json`；
- Runtime 对外接口变化更新 `toolkit/contracts/统一接口契约.md`。

公共目录或格式发生变化时仍必须完成影响分析、版本调整、迁移或重建策略、自动化测试和旧工作区检查，并在当次交付说明中写清楚；不再为此长期保存独立的变更记录文件。

## 11. Skill 获取与工作区自动适配

Studio 必须通过统一的 `SkillBundleSource` 获取 Skill，不能让业务页面依赖具体来源。

第一阶段实现：

```text
LocalDirectorySource
```

当前本地正式来源：

```text
/Users/admin/innos/easy-bi-workspace/easy-bi
```

接口层同时保留以下扩展类型，但第一阶段不要求连接远程服务：

```text
LocalArchiveSource
BuiltInSource
HttpRegistrySource
```

获取过程分为三层：

```text
Skill 来源
  → 本地不可变版本缓存
  → 复制并安装到指定工作区
```

工作区不能直接运行一个会被其他工作区更新的共享可写 Skill 目录。每次安装都写入 `skills/bundle.lock.json`，至少记录 Bundle ID、版本、SHA-256、来源类型和安装时间。一个工作区升级不得改变另一个工作区的 Skill。

用户打开初始 Skill 工作区时，Studio 自动执行：

1. 定位 `skills/bundle.manifest.json`；
2. 校验 Manifest、Skill 入口和文件哈希；
3. 没有 `workspace.json` 时按 Manifest 执行 `init`；
4. 已有工作区时执行 `check`；
5. 自动创建缺失目录、空索引和缺失模板；
6. 自动补充新增的可选配置默认值；
7. 绝不覆盖已有数据库配置、Runtime 配置、人工知识库、报表包和输出；
8. 运行依赖检查和 `doctor`；
9. 返回当前状态、自动处理结果和下一步；
10. 直接引导用户填写数据库连接和预期报表需求。

正常情况下，用户不需要选择格式版本、填写路径或手工运行初始化命令。

## 12. Bundle Manifest 规则

机器可读入口固定为：

```text
skills/bundle.manifest.json
```

Manifest 至少声明：

- Bundle ID、Bundle 版本和格式版本；
- 两个 Skill 的 ID、版本、相对路径和 Agent 入口；
- 知识库、报表包和 Runtime CLI 相对入口；
- 支持的工作区、配置、知识库、报表包和 Runtime API 版本；
- 工作区逻辑路径映射；
- 配置模板和空索引；
- 自动初始化、检查和升级策略；
- 支持的 Skill 来源类型；
- 目录兼容规范位置。

项目通过逻辑键读取路径，页面不得直接写死深层目录。仅输出目录发生兼容调整时，更新 Manifest 和工作区路径映射即可；JSON 结构或 API 语义变化仍需提升格式版本并提供适配或迁移。

Manifest 自身是冻结的公共入口：

- 允许增加可选字段；
- 不得删除或改变已有字段语义；
- 路径必须相对工作区或 Bundle 根目录；
- 发布快照时必须生成全部文件 SHA-256；
- 新 Manifest 必须经过一个新工作区初始化和一个旧工作区检查；
- 缺少或无效 Manifest 时，Studio 必须停止自动初始化并给出明确错误。

## 13. 文档维护规则

正式项目只保留以下文档职责：

| 入口 | 职责 |
|---|---|
| `docs/总体架构.md` | 产品边界、组件、流程、部署和版本基线 |
| `docs/开发维护指南.md` | 开发、测试、发布、工作区和 Studio 维护 |
| 两个 `SKILL.md` | Agent 核心工作流和执行门禁 |
| 每个 Skill 的 `使用说明.md` | 开发者和管理员的操作步骤、输入输出与常见问题 |
| 每个 Skill 的唯一技术规范 | 详细格式、判断策略和运行契约 |
| 本文件 | 公共目录、升级和跨工作区兼容 |
| `toolkit/contracts/统一接口契约.md` | Runtime 对外接口 |

不得重新引入按阶段、页面、日期、单个问题或临时测试拆分的长期设计文档。新结论更新到对应稳定入口；临时材料放入当前工作区 `work/`，任务完成后删除。

删除或合并非公共文档不改变工作区格式。修改 Skill 内引用文件时，必须同步更新 `SKILL.md`、Bundle 版本、快照哈希和新工作区测试。
